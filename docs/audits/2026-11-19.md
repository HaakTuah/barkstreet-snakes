The baseline (issue #764; the core's brief, `agent-core` `tasks/cleaning.md`). Measured at `origin/main` 70873d3 (merge of #778), the 130
script files `index.html` loads, by the scripts in `tools/dev/audit/`; read by a fresh Opus session at high effort that built none of
it and changed nothing. The eight questions are answered, each with its evidence and a scale, in `docs/audits/2026-11-19-answers.md`;
this file holds the numbers and what to do with them. The raw numbers are in `docs/audits/2026-11-19/*.json`. No game code changed.

`node tools/dev/audit/tables.js <folder> docs/audits/2026-11-19` prints each number beside this audit's. Set the two reports side by side
by the scale below. The core's `code-shape.mjs` is not in this copy of the core yet: these numbers used a read-only clone of

builder's goal"); each is the baseline a later audit and a check that "may not get worse" read against.

### Frame time (`tools/bench.js 20`, headless Chrome in software, so ratios mean more than milliseconds)

Real frames while watching a round: script time per frame median 1.5 ms at 1x (58 fps) and 2.5 ms at 4x (50 fps), none over 16.7 ms;
`step()` with every AI decision, median 1.2 ms, 99th percentile 2.7 ms (8,916 ticks). The staged scenes' full cost of a frame, 14 to 26 ms
in software rendering (the land, with a rival on it, costs 1.5 and 1.8 times its twin without). The numbers are in `frames.txt`.

### What the numbers say about the owner's report of a slow first start (#763)

The server answers 145 requests in a first visit's first 8 seconds (693 kB gzipped: the page's files and the service worker's own
fetches), and the page runs every script before the start card works. On this machine with no network cost the card is usable after 0.75 s and a
second visit takes the same, since scripts parse and run each time (script time 254 ms of 878 ms); the phone profiles, with the same files and
a latency cost on each, take 11.8 s on a good connection and 25.1 s on a poor one, the server speaking HTTP/1.1 (the live site multiplexes, so read
those two against each other and against a later audit, not as the live site's time). A second visit with the service worker takes 1.5 s on
either. The measure is kept so the owner's "faster before" can be checked on the merges of the last week (`--root` runs it on another copy);
this audit does not fix it (#763 stays the polish lane's).

## What each finding comes to

The reader's proposals (boundary, the check, what stands today) are in the answers file's "Findings and proposals". In short, in the order
it proposes the cleaning lane takes them, each its own small PR with behaviour proven unchanged (fingerprint and suites):

1. The two small drifts (the online test's list of a rival's memory lacks `'style'`; `render/core.js`'s file map lacks `shield.js`).
2. **The part check:** `tools/dev/audit/uses.js` promoted to a suite, with each part, its entrance namespace and the parts it may use named in a
   config and today's 17 crossing names as its baseline, so crossings never grow and the rules never reach the display. The core's own shape
   check reads imports, which this game has none of, and its rule "each file adds at most one name to the shared space" would list 128 of 129
   scripts; its function marks (lines, depth, branching) apply as they are and hold the big switches.
3. Split `game/friends.js` (the Hall of Fame and Field guide; the lobby) as a pure move, then one teaching file for each rule's lesson words,
   guide row and trigger, with the check that each lesson has its guide row ("always both", core-manifest).
4. The controller's round flags off the engine's `Game`; the event switches (`news`, `sounds`, `onTick`) into tables by event.
5. In main-lane slots, fingerprint identical: `DIRS` and the cast registry out of the AI's files, `decide()` returning a declared plan, `step`
   split by phase; then an engine-owned snapshot for online (a protocol version bump).

**Imports.** The reader's verdict on moving to imports now (#771): cleaning first, since A to E are worth doing with or without modules and
C, D and H would otherwise trip a move; a move ends opening `index.html` from disk (modules refuse `file://`), and the sim, `--versus` and
`abtest` load game text into fresh contexts and need reworking with their fingerprints kept; if it comes, `chatter/` goes first (22 files,
one namespace out, a Node suite of its own). Neither imports nor the checks remove the reason engine and AI work runs one at a time (one
fingerprint and one A/B baseline for the whole game): trial #768 tests that.

## What this audit did not measure

  mutation tool this game does not name. Suite times are read; the 110 failed runs of the `tests` workflow are counted.
- The core's shape check as a check (it is not in this copy of the core; its measures were run from a clone), and `strength.mjs`.
- Merge conflicts the lanes had (git does not keep resolved ones): question 2's 3 rests on the files each merged pull request touched.
- The live site's own start-up, on real phones.
- `uses.js` reads by name and scope with a reader of brackets: it read one alias wrongly at first (fixed; a later audit's numbers may rise a
  little where another reading gap is found), and its counts of the display are by shared name and namespace member, not by call.
